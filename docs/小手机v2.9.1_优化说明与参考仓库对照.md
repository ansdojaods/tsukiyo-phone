## 1. 后台与主动来信：解除限制（第 1 点）

### 1.1 改了什么

| 原行为（v2.5.1） | 现在（v2.6.0） |
| --- | --- |
| `Gate.reserve()` 断言 `近1小时 < maxHourly` 且 `近24小时 < maxDaily`，主动来信一起被卡 | 主动来信默认**不占用额度**：调度时把上限视为无限，超额只对其它模块生效 |
| `nextAutomatic()` 里 `!quiet && a.proactive…`，夜间免打扰（默认 23:00–07:00）直接拦死主动来信 | 主动来信**不受免打扰**（`proactiveIgnoreQuiet`，默认开）；免打扰只拦生活动态等模块 |
| `proactiveEvery` 最小 1、`proactiveMinutes` 最小 5，未读 3 条硬编码 | `proactiveEvery = 0` 表示**每轮回复都检查**；`proactiveMinutes = 0` 表示不额外等待；未读上限 `proactiveUnreadCap`（0 = 不限制） |
| 后台状态机遇额度满时输出“已达后台调用上限；手动操作仍可使用” | 该提示只在**非主动来信**任务上出现，并注明主动来信不受限 |

### 1.2 新增开关（后台与主动来信页）

| 字段 | 默认 | 含义 | 范围 |
| --- | --- | --- | --- |
| `proactiveUnlimited` | **开** | 主动来信不受每小时/每24小时调用上限限制 | 布尔 |
| `proactiveIgnoreQuiet` | **开** | 主动来信不受夜间免打扰限制 | 布尔 |
| `proactiveEvery` | 3 | 每隔几次酒馆回复检查一次，**0 = 每轮都检查** | 0–50 |
| `proactiveMinutes` | 20 | 两次自动调用之间的最小间隔，**0 = 不额外等待** | 0–1440 |
| `proactiveUnreadCap` | 3 | 同一角色未读达到该值先等你查看，**0 = 不限制** | 0–50 |
| `maxHourly / maxDaily` | 6 / 24 | 其它模块（动态/规划/记忆等）的额度，**不含主动来信** | 1–30 / 1–100 |

### 1.3 仍然保留的安全网（不然会失控烧额度）

1. **回复数门槛**：一轮正文没出新回复，就不会反复触发（`proactiveEvery` 语义）。
2. **最短 60 秒**：后台每 30 秒轮询一次，即使设成 0 也不会同一状态连发；失败按指数退避（最长 60 分钟），不死循环。
3. **模型可拒发**：提示词允许模型回 `send:false`（现在这一次不再计入额度，之前会白吃一次）。
4. **模块开关优先**：`proactive` 关掉、联系人 `暂停此人主动来信`、待发未发送时跳过。
5. **让行规则**：主线正在生成/你正在输入时后台让行；切换聊天立即取消在途任务。
6. **主开关不变**：`允许后台自动工作` 仍需你首次确认（记录 `consentAt`）。

> 用法：设置 → 后台与主动来信 → 勾上两个新开关 → 保存后台规则。想恢复旧版严格限流，把两个开关取消即可（额度与免打扰立即生效）。

## 2. SoulLink 算不算记忆模块的功能？（第 2 点）

### 2.1 SoulLink 是什么（核对结果）

`Rosa9527/SoulLink` 是**酒馆第三方扩展**（v1.7.5，2026-09-20；52 次提交；`manifest.json + index.js + js/* + prompts/*`），核心能力：

- **角色名单 + 角色档案**：按聊天绑定（`settings.archives`，键 = 角色名），档案分 **性格 / 世界观 / 家庭背景 / 人际关系 / 记忆** 五个分节，条目带**来源楼层**，删楼会联动清理；
- **AI 档案维护**：每轮回复生成结束后自动预筛（Gate）→ 并发增量更新档案；「分析本角色 / 分析全部 / ✨精编」；
- **发送前角色推演**：点发送后先由 Gate 选本轮有戏份的角色，再**并发**为每个角色生成一段 400 字内第一人称内心独白，注入到最后一条用户消息下方（45 秒硬超时，失败自动放行）；
- **世界书读取**：按酒馆触发规则读取当前激活世界书，可逐条排除；
- **导入导出**：`soullink-roster-<ISO>.json`（`{app, kind:'roster', version, exportedAt, chatKey, chatLabel, count, roster}`），导入语义为“新角色追加、同名覆盖”；
- 其余：OpenAI 兼容 API、并发上限（默认 3）、最大输出 tokens、思考强度、日志系统、四套主题、API 正则过滤。

### 2.2 结论：**算记忆模块的功能，但它是“NPC 档案型记忆 + 生成前 NPC 推演”**

- 小手机现有记忆模块负责的是**事实型记忆**：交流事实、正文事实、未完约定、滚动摘要 + 记忆世界书（双向同步、冲突以世界书为准）。
- SoulLink 负责的是**人物型记忆**：一个 NPC 的长期档案（性格/世界观/家世/人际/记忆条目）会随剧情**增量沉淀**，并在生成正文前把“这个角色此刻在想什么”喂给主模型。这两件事互不替代，属于记忆系统的两个面。
- 所以不建议把 SoulLink 的代码搬进小手机（它是独立扩展、有自己的 API 与设置面板，重复实现会双重注入、双重计费）。正确做法是**桥接**：读它的档案、往它的「记忆」分节追加，或用文件互通。
- **v2.8.0 补充**：桥接之后又往前走了一步 —— 用手机自己的 API 路由实现了**同一套功能模型**（名单 + 五节档案 + 预筛自动维护 + 发送前推演），数据格式与 SoulLink 的 `roster` JSON 完全互通。**不装那个扩展也能用**；装了也可以把档案导进来。为什么不直接复制它的代码，见 **§8.1**。

### 2.3 已实现的桥接（设置页 → SoulLink 联动）

| 通道 | 行为 | 默认 |
| --- | --- | --- |
| 检测 | 在 `extensionSettings` 里自动寻找含 `archives / roster / characters` 的扩展键（也兼容你手动指定键名），并自动匹配当前聊天那一份档案 | 只读 |
| 导入到手机 | 每个角色 → 手机联系人：资料写入「SoulLink 档案」参考资料；其「记忆」分节 → 手机记忆条目（带 `sl` 标记，**不会**写进记忆世界书，避免与 SoulLink 自己的注入重复） | 手动按钮 |
| 写回 SoulLink | 把最近交流、约定、恋爱心迹、日记整理成 `【小手机·…】` 短条目，追加到对应角色的「记忆」分节（同内容去重），并触发酒馆保存设置 | **默认关闭**，需显式打开 |
| 文件互通 | 「导出 SoulLink 名单（JSON）」= 与 SoulLink 导出同结构，可直接用它的「导入」按钮；「导入 SoulLink 名单（JSON）」兼容 `roster / archives / characters / data / items` 与裸映射，做结构清洗后并入手机 | 手动按钮 |

边界与风险：
- 写回是对**另一个扩展的设置**写入。协议上只碰你自己的档案数据，且会先调用它自己的保存流程；但仍建议先在 SoulLink 里导出一次名单做备份（按钮旁已写明）。
- 若你的聊天里已经在用 SoulLink 的「自动档案维护」，建议手机侧**只读**（不开写回），避免同一段交流被两边各记一遍。

## 3. 手机数据 ↔ 记忆模块 / 世界书（第 3 点 + 第 5 点）

### 3.1 新模块：世界书工坊（首页 → 世界书）

和既有「记忆世界书」**分工并行**（互不冲突、各管各的条目）：

| | 记忆世界书（v2.5.1 已有） | 世界书工坊（v2.6.0 新增） |
| --- | --- | --- |
| 管什么 | 手机**记忆条目**（交流事实/正文事实/未完约定/手工记忆） | **日记、恋爱心迹、会话摘要、人物档案（NPC 性格与资料）、约定与日程、备忘便签、生活清单** |
| 条目标记 | `extra.tsukiyo.id`（记忆编号） | `extra.tsukiyo.source = "book-studio"` + 类型 + 稳定键 + 内容哈希 |
| 冲突 | 世界书版本优先，旧内容可在记忆页恢复 | 世界书版本优先，手机旧文保留在行的 `prev` / 日志 |
| 条目上限 | 单条 8000 字以上不导入 | 同上，并统计“跳过” |

两者的条目会互相忽略（已加 `foreign` 过滤），不会出现“工坊条目被记忆模块误导入”这类串味问题（已测试）。

### 3.2 支持的数据类型（可分别开关）

| 类型 | 条目名示例 | 关键词（触发） | 世界书改动能回到手机吗 |
| --- | --- | --- | --- |
| 角色与玩家日记 | `【小手机】[日记] 1604-09-03 宫里的一天` | 日期、作者、正文提到的人物名 | ✅ 回写正文 |
| 恋爱心迹 | `【小手机】[心迹] #5楼 临安` | 角色名、楼层 | ✅ 回写正文 |
| 会话摘要 | `【小手机】[摘要] 临安` | 会话成员、`会话摘要` | ✅ 回写摘要 |
| 人物档案（NPC 性格与资料） | `【小手机】[人物] 慕南栀` | 姓名、别名、标签（可设“常驻”） | ⚠️ 不回写人设，改为在人物页新增「世界书同步」参考资料 |
| 约定与日程 | `【小手机】[约定] 1604-09-05 河灯埠看灯` | 日期、参与人 | ✅ 回写备注 |
| 备忘便签 | `【小手机】[备忘] 买蜡烛` | 正文提到的人物名 | ✅ 回写正文 |
| 生活清单 | `【小手机】[清单] 学会挑一件礼物` | 标题里的人物名 | ❌ 只写不取（避免误改进度） |

写入细节可调：**条目前缀**（默认 `【小手机】`）、**条目上限**（默认 400，按时间保留最新）、**是否取回手机改动**、**人物档案是否常驻**。

### 3.3 创建步骤（第 5 点：创建世界书模块）

1. 首页 → **世界书** → 「创建并同步」；
2. 填写世界书名称（默认 `角色卡名-小手机世界书`）；范围二选一：
   - **整张角色卡共用**：这张卡以后新开的聊天共用同一本（推荐，跨存档记忆）；
   - **仅本聊天**：每聊天一本，互不混；
3. 选择首次写入内容（推荐 / 轻量 / 只写人物档案）；
4. 创建后会**追加绑定**到角色卡或聊天世界书（不动你原有的绑定），随后立即做一次同步；
5. 在酒馆的世界书面板里可以直接看、改、删这些条目——它们就是普通条目（关键词触发，人物档案可设常驻），模型按酒馆规则读取。

**为什么走世界书而不是只留在手机里**：世界书是跨模型、跨存档最稳的“可读记忆层”，主模型不必额外调用手机；手机负责采集（日记/心迹/摘要），世界书负责注入。

**注意事项**
- 世界书条目会占上下文：默认按关键词触发（人物名/日期），人物档案默认不常驻；想更稳可以逐类打开“常驻”。
- 删除保护：如果世界书里被一次性删掉太多（≥5 条且超过一半），工坊会先暂停并让你确认（“按世界书删掉对应条目”或“以手机数据重建”）。
- 与柏宝书三方共存建议：**只选一条注入路径**。要么让柏宝书注入正文、手机只读（现状），要么用世界书工坊；同一段记忆重复注入会浪费上下文。
- 若同时用记忆世界书 + 世界书工坊，建议两本分开（`-小手机记忆` / `-小手机世界书`），便于单独开关。

### 4.2 建议清单（按优先级，均已评估过现有代码结构）

**P0（收益高、风险低、改动小）**
1. **后台调度账本页**：现在只有“近1小时/近24小时”两个数字；建议按模块显示最近一次调用、下一次可调用时间、失败与退避状态（数据都在 `automation.last/next/failures`，只差 UI）。
2. **世界书写入串行队列**：记忆世界书、工坊、视觉各自会 `wbUpdate`，极端情况下并发会互相覆盖。建议在 `TavernBridge` 加一把“世界书写锁”（队列化，串行执行）。
3. **主动来信话题冷却**：把最近 N 次主动来信的 `reason` 记下来，提示词里排除，减少“同一件事反复找你”。
4. **一键“导出全部手机数据”**：现在有完整备份，但缺“可读文本导出”（Markdown/JSON 分文件），用在排查与迁移。

## 7. v2.7.0 追加优化（第二次优化）

### 7.1 世界书写入串行队列（并发安全）
**问题**：记忆世界书、世界书工坊、柏宝书回写、视觉模块都会调用 `updateWorldbookWith`。同一个世界书被两处同时改时，两边各自基于“改之前的旧副本”重写，后写入的那次会把前一次的条目覆盖掉（表现为“刚同步的条目偶尔消失”）。

## 8. v2.8.0 追加优化（第三次优化）：把 SoulLink 的功能“内置”进来

### 8.1 先说结论：能复制，但不值得直接复制

| 检查项 | 查到的事实 | 影响 |
| --- | --- | --- |
| 许可 | `Rosa9527/SoulLink` 仓库**没有 LICENSE 文件**（GitHub API 返回 `"license": null`） | 直接搬运代码进你的仓库**没有授权依据**，连署名都补不齐 |
| 体积 | 打包产物 `index.js` = 623 KB；`js/` 源码约 700 KB（`constants.js` 120 KB、`archive-analysis.js` 65 KB、`ui-shell.js` 52 KB、`views-log.js` 34 KB、`prompts.generated.js` 34 KB…） | 小手机脚本本身 1.1 MB，塞进去体积翻倍，加载与后续维护都上一个台阶 |
| 重复 | 它本来就是**独立扩展**：酒馆里装一份、小手机里再内置一份，等于同一个功能两套设置、两套数据 | 容易出现“两个面板各记一半”，还可能双重调用模型、双重计费 |
| 结论 | 走**功能等价的原生实现** + **数据格式互通**（`roster` JSON 互导） | 不装扩展也能用；装了也能互相导档案；体积只增加约 50 KB |

> 这也是你原话「能复制就直接复制原仓库的」的最优解：复制代码这条路被“没有许可证 + 体积翻倍 + 功能重复”三件事堵住，但**功能与数据是完整对齐的**（下面每一条都对照它的行为实现）。

### 8.2 内置「灵魂链接」的数据模型（与 SoulLink 对齐）

- 名单：`soul.roster[角色名] = { name, aliases[], sections{性格/世界观/家庭背景/人际关系/记忆}, enabled, source, updatedAt, floor }`
- 每条档案：`{ id, text(≤600字), floor(来源楼层，-1 = 未标注), source(manual | ai | phone | import | condense), ts }`；每节默认最多 60 条（超出丢最旧）
- 参数：并发 1–8（默认 3）、单个请求超时 5–180 秒（默认 45）、上下文 1–20 条（默认 4）、独白字数 80–800（默认 400）、注入深度 0–10（默认 4）、每节条目上限 10–60
- 档案存在**手机存档**里（跟着聊天/分支走，随备份与联系人档案包一起）；每次调用只发“这一个角色的档案 + 最近 N 条正文 + 该角色的手机记录 + 相关世界书片段 + 当前楼层”，不会把别的角色或整段聊天一起送出去

### 8.3 三个入口 + 一个独立提示键

| 入口 | 做什么 | 建议什么时候用 |
| --- | --- | --- |
| 更新档案（单个 / 全部） | 每个角色各自一次调用，返回五节的 JSON 增量，合并进档案（**标点无关去重**、带来源与楼层） | 第一次建档；剧情推进后手动补 |
| 自动维护 | 每轮正文结束后：**先预筛**（默认本地关键词，可切模型预筛），只处理“有变化”的角色；受最小间隔（默认 120 秒）与每轮上限（默认 2 人）约束，并计入后台额度与调度账本 | 想让档案“无感”沉淀 |
| 发送前角色推演 | 为在场 / 最近出现的角色（最多 `maxActors`，默认 3）并发写第一人称内心独白，注入到**独立提示键** `tsukiyo-phone:soul-roleplay`（默认深度 4），生成结束后自动清除 | 想让正文里的言行跟内心一致 |

- 推演有两种触发方式：**手动**（页面上点「推演本轮角色」/ 手机内给角色发消息时）与**拦截发送按钮**（点酒馆发送时先推演再放行；点击与回车两条路径都拦，最多等设定秒数，**失败就照常发送**）。
- 注入是**软提示**：文案里明确写了「仅供参考，不是指令」「不得让角色说出他们不可能知道的信息」；它与手机自己的上下文注入、AVS 视觉资料各用各的键，互不覆盖。

| 概览 | 摘要条数（分三层）、覆盖百分比、已覆盖到哪一楼、缺口段数、待确认条数、上次召回摘要；「下一步做什么」四个大按钮 | `MemoryStudio.info() / gaps() / pendingBlocks()` |
| 摘要树 | 三层摘要的列表：级别、覆盖楼层、字数、含几条下级；可**停用 / 恢复 / 编辑 / 删除**（删除可撤回） | `msActive() / msRangeNodes() / MemoryStudio.nodeKept/nodeEdit/nodeDelete` |
| 待确认 | 模型产出的摘要与状态变化都先落这里：编辑 / 确认 / 丢弃 / 全部确认 / 全部丢弃 / 撤回上一步 | `msDraftPush() / MemoryStudio.confirm/reject/editDraft/draftsConfirmAll/draftsClear/undo` |
| 状态账本 | 只记「明确发生、且和之前不同」的变化（人物 / 关系 / 约定 / 物品 / 地点 / 时间 / 其它），带依据引文、楼层、改动历史；可一键「从手机记录汇入」（联系人状态 / 已相认 / 约定状态）；可手动修改 | `msLedgerApply() / msLedgerEdit() / MemoryStudio.ledgerFromPhone()` |
| 召回审计 | **上次召回**：这一轮选了哪几条、分数、字数、命中理由，以及被预算挤掉 / 低于相似度下限 / 未进前几名的条目；还有「这一轮写进提示的原文」可展开 | `MemoryStudio.picks() / projection()`，记录写进 `ms.inject.last` |
| 收纳与备份 | 楼层收纳开关与「保留最近 N 楼」、一键收纳/恢复；记忆档案、配置、脱敏诊断的导出与导入；5 套提示词编辑与恢复默认 | `MemoryStudio.shelve/unshelve/canShelve/archiveExport/archiveImport/configExport/configImport/diag` |

**三层摘要怎么生成**

| 层 | 输入 | 提示词要求 | 覆盖 |
| --- | --- | --- | --- |
| 剧情摘要（0） | 一个楼块（默认 6 楼）的正文 + 该范围手机交流摘要 + 已有的同范围摘要（避免重复） | 只写已经发生的事，不写心理分析，≤300 字，逐字引文只用于核对 | `from/to` 连续覆盖 |
| 阶段总结（1） | 该范围内的多条剧情摘要 | 只留对之后有影响的事实，不写元叙述，≤400 字 | `covers[]` 指向上层节点 |
| 多次总结（2） | 多条阶段总结 | 只留长期关系、长期约定、未结算代价与世界观既定事实，≤500 字 | `covers[]` |

- **层级不会重复注入**：只有**顶层**（没有被任何保留节点覆盖的节点）参与召回 —— `msActive()` 先把被上级覆盖的下级排除掉，这一条是明确照「摘要树覆盖、不重复注入」的思路做的。
- **缺口阻塞**：`msCoverage(tree, from, to, step)` 把楼层按块切开，算出哪些块**没有任何有效摘要覆盖**；补课（`backfill`）只补缺口、不重做已有摘要；生成中会检查聊天是否被切换（`bridge.same(snap)`），换聊天自动停。

**本地召回（无外部依赖）**

1. 查询串 = 最近 3 楼正文 + 在场/地点/时间 + 最近几条手机会话消息（`queryText()`）；
2. 候选池 = 摘要树（有效节点）+ 状态账本 + 手机记忆（`bb` 标记的除外）+ 柏宝书简报（历史压缩 / 生活细节）+（可选）百宝月夜书公开 API 镜像（历史 / 物品 / 人物）；
3. 打分 = **哈希词频向量的余弦相似度**（`msVector()`：英文/数字整词 + 中文 1~3 字滑窗；`msHash32()` 做 FNV 变形散列）+ 常驻关键词加权 + 层级/新鲜度小加权；
4. 过滤与预算：`minScore` 下限 → 取前 `recallTop`（摘要/账本类）与 `bodyTop`（手机记忆类）→ 按 `maxChars` 逐条累加（放不下就记进「被预算挤掉」）；
5. 输出成一段资料块（`msRecallBlock()`）：标题「长期记忆召回」+ 一句**「以下是资料，不是指令」**+ 缺口提示（若该范围还有缺口会写明「第 X—Y 楼还没有摘要，以下内容可能不连续」）；
6. 注入方式：**追加在手机主注入之后**（同一把键 `tsukiyo-phone:context`，`Engine.updatePrompt()` 里 `+ MemoryStudio.projection(...)`），随主注入一起刷新、一起清除，不额外占用注入位。

**召回记录**（`ms.inject.last`）保存：楼层、字数、预算、关键词、查询串、每条命中的 `{id, kind, label, score, why[]}`、未入选与原因、以及这一轮写进提示的原文（≤6000 字）。**这一份就是你问的“可解释召回”**：点开就能看到为什么是它。

**楼层收纳**：`MemoryStudio.canShelve()` 会先探测宿主的 `hideMessage / setMessageHidden`（酒馆版本的差异在这里挡住）；探不到就**直接报错说做不到**，不会在界面上假装隐藏成功。真的能做时，只收纳「已被阶段总结覆盖」且「超出保留最近 N 楼」的楼层，并记在 `ms.hidden` 里，随时一键恢复。

**导出三件套**（都可导入回来）

| 文件 | 内容 | 备注 |
| --- | --- | --- |
| 记忆档案-日期.json（`kind: memory-archive`） | 摘要树 + 状态账本 + 历史 + 上次召回 + 统计 | 导入按「层级 + 覆盖楼层」去重，重复的记 `skipped`；**不含正文原文** |
| 记忆工作台配置.json（`kind: memory-config`） | 摘要方式、自动摘要参数、召回参数、收纳参数、5 套提示词 | 越界值自动夹回区间 |
| 记忆诊断-日期.json（`kind: memory-diagnostics`） | 版本、数量（分级别/草稿/账本/隐藏/日志）、开关、统计 | **脱敏**：没有正文、没有角色名、没有端点或密钥，可以直接贴给别人看 |

### 9.7 未落地 / 已知限制（诚实清单）

1. **OpenAI 兼容 Embedding 召回**没做：默认只有本地哈希向量检索。要做的话是加一个可选端点（手机里已有 `api-router`，接起来不难），但会引入额外额度与密钥管理，暂留作后续。
2. **旧正文补课（改写既有楼层）**没做：手机只新增摘要草稿，不修改你已有的楼层内容。
3. **移动端警示**没做：手机本身是窄屏 UI，相关提示写在卡片文案里。
4. **公开 API 的 HTTP 地址是推断值**：默认 `/api/plugins/st-baibai-book/bbs-get` 是按酒馆插件路由习惯猜的；你文档里只明确定义了 `/bbs-get` 指令，所以默认走**指令方式**，HTTP 方式取不到就换回来（界面与报错里都写了）。
5. **`ui.route.view = "ms"` 没有进首页磁贴**：入口放在「记忆」页顶部卡片里（首页已经有 15 个磁贴，再塞一个会更挤）。要磁贴的话在 `ui/renderer.js` 的 `apps` 数组加一行即可。
6. **楼层收纳依赖宿主接口**：酒馆版本没有 `hideMessage / setMessageHidden` 时只记录不隐藏（并明说）。
7. **召回质量取决于摘要质量**：所以才有「待确认」这一道闸；如果摘要草稿一直被丢弃，召回里就会缺少该段记忆，缺口列表也会一直提醒你。

## 10. v2.9.1：楼层记忆归属互斥（不要重复）

### 10.1 为什么要做
v2.9.0 的记忆工作台把「楼层摘要 + 缺口 + 召回注入」做进了手机。同日我们确认了最终分工：
**楼层记忆归记忆引擎（百宝月夜书）**，因为楼层归属（`mesid`、失效与番外判断、`coverage.missingAiFloors`）
和注入通道都在引擎手里。如果两边各建一棵摘要树，同一段剧情会被注入两次、缺口数字互相打架、
推演与召回也会互相矛盾——这是本方案里**唯一不能接受**的状态。

### 10.2 手机侧怎么改的（默认打开）
| 触发 | 行为 |
| --- | --- |
| `STBaiBaiBook.memoryEditor.capability()` 返回 `available: true` | 进入「引擎接管」 |
| 自动摘要（生成结束 / 定时巡检） | 停用，只把引擎镜像同步进存档（节流 10 秒） |
| 召回注入 | 默认整体让给引擎；打开「接管期间仍注入手机内记忆」后**只**注入 `kind === "memory"` 的手机自己的记忆 |
| 剧情摘要 / 阶段总结 / 多次总结 / 状态核对 / 补课 | 报错引导：「已交由百宝月夜书管理，请到那边的剧情剪辑台操作」 |
| 记忆 → 记忆工作台 | 顶部新增「楼层记忆归属」卡片：接管状态、引擎版本、覆盖率、缺口段数、上次召回、两个开关与「重新探测引擎」 |
| 探测失败 / 引擎不在 | 一律当「没装」，行为与 v2.9.0 完全一致（手机自己管，功能不缺失） |

**只读**：手机只调用 `capability()` 与 `mirror()`，不写引擎的任何数据；手机记录仍按老通道
（`pushNotes` / 世界书工坊 / 1.6.3 事项生命周期）单向交给引擎。

### 10.3 引擎侧要补的东西
把「剧情剪辑台」挂到 `window.STBaiBaiBook.memoryEditor`（`apiVersion` 仍为 1），至少提供：
- `capability()` → `{ available: true, apiVersion: 1, pluginVersion }`
- `mirror()` → `{ updatedAt, enabled, mode, coverage{ratio,missing,step}, summaries[], ledger[], counts{summaries,active,drafts,ledger,hidden}, lastRecall{floor,chars,budget,hits[]} }`

引擎侧的完整实现（摘要树 / 状态账本 / 缺口 / 召回 / 收纳 / 草稿 / 撤回 / 脱敏诊断 + 55 项测试）
已单独打包：`baibai-memory-editor-1.4.0.zip`（对应百宝月夜书 1.3.4 → 1.4.0），
对接说明见该包 `README.md` 与 `docs/剪辑台迁移方案.md`。
